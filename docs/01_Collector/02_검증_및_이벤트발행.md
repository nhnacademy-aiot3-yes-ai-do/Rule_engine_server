# 02. 검증 및 이벤트 발행

파싱된 `SensorDataDto`를 검증하고, 통과한 데이터를 이벤트로 발행하여 RuleEngine에 전달하는 부분입니다.

## 1. CollectorService

`CollectorService`는 실질적인 파싱·검증 로직을 직접 수행하지 않고, 아래 컴포넌트들을 순서대로 호출하여 흐름을 조율합니다.

```java
@Service
public class CollectorService {

    private final List<SensorDataParser> sensorDataParserList;
    private final SensorDataValidator sensorDataValidator;
    private final ApplicationEventPublisher eventPublisher;

    public void ingest(String topic, String payload) {

        SensorDataParser parser = sensorDataParserList.stream()
                .filter(p -> p.supports(topic))
                .findFirst()
                .orElseThrow(() -> new UnsupportedTopicException(topic));

        List<SensorDataDto> dtoList;
        try {
            dtoList = parser.parse(topic, payload);
        } catch (InvalidTopicFormatException | InvalidPayloadFormatException e) {
            log.warn("파싱 실패 - 폐기: {}", e.getMessage());
            return;
        } catch (Exception e) {
            log.error("예상치 못한 오류 파싱 에러", e);
            return;
        }
        dtoList.forEach(this::validateAndPublish);
    }

    private void validateAndPublish(SensorDataDto sensorDataDto) {
        sensorDataValidator.validate(sensorDataDto)
                .ifPresentOrElse(
                        sensorData -> eventPublisher.publishEvent(new SensorDataReadyEvent(sensorData)),
                        () -> log.warn("[Collector - Validation] 검증 실패: {}", sensorDataDto)
                );
    }
}
```

1. 수신한 토픽을 지원하는 `SensorDataParser`를 찾습니다. 없으면 `UnsupportedTopicException`을 던집니다.
2. 파서로 파싱을 시도합니다. `InvalidTopicFormatException`/`InvalidPayloadFormatException`이 발생하면 경고 로그만 남기고 해당 메세지를 폐기합니다. (RuleEngine으로 전달하지 않음)
3. 파싱된 각 `SensorDataDto`에 대해 검증 및 이벤트 발행을 진행합니다.

## 2. SensorDataValidator

```java
@Component
public class SensorDataValidator {

    private final SensorInfoService sensorInfoService;
    private final ManagedSensorTypeService managedSensorTypeService;

    public Optional<SensorDataDto> validate(SensorDataDto sensorDataDto) {

        if (!managedSensorTypeService.isManaged(sensorDataDto.getSensorType())) {
            log.warn("미관리 센서 타입 데이터 폐기: ...");
            return Optional.empty();
        }

        if (sensorDataDto.getValue() == null) {
            log.warn("센서 값이 null인 데이터 폐기: ...");
            return Optional.empty();
        }

        Optional<SensorInfoDto> sensorInfo = sensorInfoService.findSensorInfo(
                sensorDataDto.getDeviceEui(), sensorDataDto.getSensorType(), sensorDataDto.getUnit());

        if (sensorInfo.isEmpty()) {
            log.warn("미등록 센서 데이터 폐기: ...");
            return Optional.empty();
        }

        return Optional.of(sensorDataDto.withCultivationId(sensorInfo.get().getCultivationId()));
    }
}
```

검증은 순서대로 다음 3가지를 확인하며, 하나라도 실패하면 그 즉시 빈 `Optional`을 반환하고 폐기합니다.

1. **관리 대상 센서 타입인지** — `ManagedSensorTypeService.isManaged(sensorType)`로, Registry가 관리하는 인메모리 캐시를 조회합니다. (자세한 내용은 [02_Registry/00_구조](../02_Registry/00_구조.md) 참고)
2. **값이 null이 아닌지**
3. **등록된 센서인지** — `SensorInfoService.findSensorInfo(deviceEui, sensorType, unit)`로 Redis에 동기화된 센서 정보를 조회합니다. 조회에 성공하면 그 센서가 속한 `cultivationId`를 `sensorDataDto`에 채워 넣어 반환합니다.

> 물리적으로 유효한 값 범위(예: 온도 -20~60°C)에 대한 별도 검증은 현재 구현에 없습니다. 등록 여부와 null 여부만 확인합니다.

## 3. 이벤트 발행 (Collector → RuleEngine)

별도의 메시지 브로커 없이, Spring의 `ApplicationEvent`와 `@Async`를 이용해 비동기로 전달합니다.

```java
@AllArgsConstructor
@Getter
public class SensorDataReadyEvent {
    private final SensorDataDto sensorDataDto;
}
```

```java
@Component
public class SensorDataReadyEventListener {

    private final RuleEngine ruleEngine;

    @Async("taskExecutor")
    @EventListener
    public void handleSensorDataReady(SensorDataReadyEvent event) {
        try {
            ruleEngine.start(event.getSensorDataDto());
        } catch (Exception e) {
            log.error("RuleEngine 처리 중 예외 발생: sensorDataDto={}", event.getSensorDataDto(), e);
        }
    }
}
```

```text
[검증 통과한 SensorDataDto]
        ↓
eventPublisher.publishEvent(new SensorDataReadyEvent(...))
        ↓
   (@Async("taskExecutor"), 호출자는 대기하지 않고 즉시 리턴)
        ↓
Spring이 이벤트 타입을 보고 SensorDataReadyEventListener.handleSensorDataReady(...)를 자동 매칭
        ↓
   ruleEngine.start(sensorDataDto)
```

- `RuleEngine.start(...)`에서 발생한 예외는 리스너 단에서 캐치하여 로그만 남기고, MQTT 수신 스레드나 이벤트 발행자 쪽으로 전파되지 않습니다.

### `@Async` 스레드 풀 (`AsyncConfig`)

```java
@EnableAsync
@Configuration
public class AsyncConfig {

    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        // corePoolSize=5, maxPoolSize=20, queueCapacity=500, prefix="collector-event-"
        // RejectedExecutionHandler = CallerRunsPolicy
    }

    @Bean(name = "mqttIngestExecutor")
    public Executor mqttIngestExecutor() {
        // corePoolSize=5, maxPoolSize=10, queueCapacity=100, prefix="mqtt-ingest-"
        // RejectedExecutionHandler = CallerRunsPolicy
    }
}
```

MQTT 메세지 수신 처리(`mqttIngestExecutor`)와 RuleEngine으로의 이벤트 전달(`taskExecutor`)은 서로 다른 스레드 풀을 사용합니다. 두 풀 모두 큐가 가득 차면 `CallerRunsPolicy`(작업을 제출한 스레드가 직접 실행)로 처리하여, 작업이 유실되지 않는 대신 상황에 따라 호출 스레드가 지연될 수 있습니다.
