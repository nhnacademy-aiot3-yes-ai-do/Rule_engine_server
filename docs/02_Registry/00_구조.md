# 00. Registry 구조

재배 환경별 임계값 정보(`ThresholdInfo`)와 센서 등록 정보(`SensorInfo`)의 원본은 `cultivation-server`가 관리합니다. Registry 모듈은 그 정보가 등록·수정·삭제될 때마다 RabbitMQ로 발행되는 이벤트를 구독하여 우리 쪽 Redis에 반영해두고, Collector의 검증과 RuleEngine의 판단 시 조회하는 용도로 사용합니다.

`registry`는 `component`(Consumer) / `service` / `repository`로 구분됩니다.

- **component** : `@RabbitListener`를 통한 이벤트 수신
- **service** : 수신한 이벤트를 바탕으로 부가 로직을 수행한 뒤 `repository`에 위임
- **repository** : Redis에 대한 실제 저장·조회·삭제

두 도메인(`ThresholdInfo`, `SensorInfo`)은 서로 다른 큐를 사용하며, 이벤트 형태도 다릅니다.

```text
ThresholdInfoConsumer
└── consumeThresholdInfoEvent(ThresholdInfoEvent)   ← 등록/수정/삭제 통합 (리스트가 비어있으면 삭제)

SensorInfoConsumer
├── consumeSensorInfoUpsertEvent(SensorInfoUpsertEvent)  ← 생성/수정
└── consumeSensorInfoDeleteEvent(SensorInfoDeleteEvent)  ← 삭제
```

---

## 1. Component (Consumer)

### 1-1. ThresholdInfoConsumer

임계값 정보는 등록/수정/삭제 이벤트가 하나의 DTO(`ThresholdInfoEvent`)로 통합되어 있어, 큐 하나에 리스너 메서드도 하나입니다.

```java
@Component
public class ThresholdInfoConsumer {

    private final ThresholdInfoService thresholdInfoService;

    @RabbitListener(queues = "${custom-rabbitmq.queue.threshold-info}", errorHandler = "validationErrorHandler")
    public void consumeThresholdInfoEvent(@Payload @Valid ThresholdInfoEvent thresholdInfoEvent) {
        thresholdInfoService.processThresholdInfoEvent(thresholdInfoEvent);
    }
}
```

```java
public class ThresholdInfoEvent {
    private Long cultivationId;
    private List<SensorRange> sensorRangeList;  // 비어있으면 삭제, 1개 이상이면 등록/수정
    private OffsetDateTime occurredAt;
}
```

- `sensorRangeList`가 빈 리스트면 **삭제**, 1개 이상이면 **등록/수정**으로 처리합니다. (별도의 delete DTO가 없습니다)

### 1-2. SensorInfoConsumer

센서 정보는 생성/수정과 삭제의 필드 구성이 달라 DTO가 분리되어 있고, 하나의 큐에서 `@RabbitHandler`로 타입별 자동 분기합니다.

```java
@RabbitListener(queues = "${custom-rabbitmq.queue.sensor-info}", errorHandler = "validationErrorHandler")
@Component
public class SensorInfoConsumer {

    private final SensorInfoService sensorInfoService;

    @RabbitHandler
    public void consumeSensorInfoUpsertEvent(@Payload @Valid SensorInfoUpsertEvent event) {
        sensorInfoService.upsertSensorInfo(event);
    }

    @RabbitHandler
    public void consumeSensorInfoDeleteEvent(@Payload @Valid SensorInfoDeleteEvent event) {
        sensorInfoService.deleteSensorInfo(event);
    }
}
```

메시지가 어떤 DTO로 역직렬화될지는 메시지 헤더(`__TypeId__`)와 `RabbitMqConfig`에 등록된 `idClassMapping`을 통해 결정됩니다.

```java
idClassMapping.put("threshold.crud", ThresholdInfoEvent.class);
idClassMapping.put("sensor.upsert", SensorInfoUpsertEvent.class);
idClassMapping.put("sensor.delete", SensorInfoDeleteEvent.class);
```

토폴로지(`RabbitTopologyConfig`)는 Topic Exchange(`custom-rabbitmq.exchange.from-cultivation` = `yes-nhn.sensor.exchange`) 하나를 두고, 라우팅 키 `threshold.*`는 `threshold-info` 큐로, `sensor.*`는 `sensor-info` 큐로 바인딩합니다. 두 큐 모두 `x-dead-letter-exchange=yes-nhn.dlx`가 설정된 durable 큐입니다.

### 1-3. 검증 및 예외 처리

- 수신한 메세지는 `@Payload @Valid`로 각 DTO의 Bean Validation 제약을 검증합니다. (`RabbitValidationConfig`가 `LocalValidatorFactoryBean`을 리스너 등록에 연결)
- 메세지 파싱(JSON → DTO) 실패, 검증 실패는 모두 `RabbitErrorHandlerConfig`의 `validationErrorHandler`가 공통으로 처리합니다. 실패한 메세지는 원본 바이트와 함께 경고 로그로 남기고 폐기하며, 재시도나 별도 DLQ 라우팅 로직은 컨슈머 코드에 없습니다.

## 2. Service

### 2-1. ThresholdInfoService

```java
@Service
public class ThresholdInfoService {

    private final ThresholdInfoRepository thresholdInfoRepository;
    private final ManagedSensorTypeService managedSensorTypeService;

    public void processThresholdInfoEvent(ThresholdInfoEvent thresholdInfoEvent) {

        if (thresholdInfoEvent.getSensorRangeList().isEmpty()) {
            thresholdInfoRepository.deleteByCultivationId(thresholdInfoEvent.getCultivationId());
            return;
        }

        validateDistinctSensorTypes(thresholdInfoEvent.getSensorRangeList());

        ThresholdInfoDto dto = thresholdInfoRepository.findByCultivationId(thresholdInfoEvent.getCultivationId())
                .orElseGet(() -> ThresholdInfoDto.from(thresholdInfoEvent.getCultivationId(), List.of()));

        thresholdInfoEvent.getSensorRangeList().forEach(dto::applyRange);
        thresholdInfoRepository.upsert(dto);

        registerSensorTypes(thresholdInfoEvent.getSensorRangeList());
    }

    public Optional<ThresholdInfoDto> findCultivationInfo(Long cultivationId) {
        return thresholdInfoRepository.findByCultivationId(cultivationId);
    }
}
```

- 등록/수정 시, Redis에 이미 저장된 `ThresholdInfoDto`가 있으면 그 위에 새로 들어온 `SensorRange`만 `applyRange`로 덮어씁니다(맵에 `sensorType_unit`을 키로 저장). 즉 한 재배 환경에 여러 센서 타입의 임계값이 서로 다른 시점에 각각 도착해도 기존 값이 유실되지 않습니다.
- 같은 이벤트 안에 `(sensorType, unit)` 조합이 중복되면 `IllegalArgumentException`을 던집니다.
- 등록/수정된 `SensorRange`의 `sensorType`은 `ManagedSensorTypeService.registerAll(...)`로 관리 대상 센서 타입 목록에도 함께 등록됩니다.

### 2-2. SensorInfoService

```java
@Service
public class SensorInfoService {

    private final ThresholdInfoRepository thresholdInfoRepository;
    private final SensorInfoRepository sensorInfoRepository;

    public void upsertSensorInfo(SensorInfoUpsertEvent event) {

        SensorInfoDto dto = SensorInfoDto.from(event);

        if (!thresholdInfoRepository.existsByCultivationId(dto.getCultivationId())) {
            // 재배 환경(임계값) 등록 이벤트보다 센서 등록 이벤트가 먼저 도착한 경우.
            // 메세지 도착 순서가 보장되지 않는 비동기 환경에서 정상적으로 발생할 수 있으므로,
            // 경고 로그만 남기고 저장 자체는 막지 않습니다.
            log.warn("센서가 추가될 재배 환경이 존재하지 않음: ...");
        }

        sensorInfoRepository.upsert(dto);
    }

    public Optional<SensorInfoDto> findSensorInfo(String deviceEui, String sensorType, String unit) {
        return sensorInfoRepository.findByDeviceEuiAndSensorType(deviceEui, sensorType, unit);
    }

    public void deleteSensorInfo(SensorInfoDeleteEvent event) {
        if (!sensorInfoRepository.existsByDeviceEuiAndSensorType(event.getDeviceEui(), event.getSensorType(), event.getUnit())) {
            log.warn("삭제하려는 센서가 존재하지 않음: ...");
        }
        sensorInfoRepository.deleteByDeviceEuiAndSensorType(event.getDeviceEui(), event.getSensorType(), event.getUnit());
    }
}
```

- 존재 확인 실패(재배 환경 미존재, 삭제 대상 미존재) 모두 처리를 막지 않고 경고 로그만 남깁니다. 이벤트 도착 순서가 보장되지 않는 비동기 환경에서, 이런 상태는 이례적이지만 정상적인 흐름일 수 있기 때문입니다.

### 2-3. ManagedSensorTypeService

Collector 검증 과정에서 `sensorType`이 관리 대상인지 빠르게 확인할 수 있도록, Redis 조회 없이 인메모리 캐시로 관리합니다.

```java
@Service
public class ManagedSensorTypeService {

    private final ManagedSensorTypeRepository managedSensorTypeRepository;
    private final Set<String> cache = ConcurrentHashMap.newKeySet();

    @PostConstruct
    void loadCache() {
        cache.addAll(managedSensorTypeRepository.findAll());
    }

    public void register(String sensorType) {
        managedSensorTypeRepository.register(sensorType);
        cache.add(sensorType);
    }

    public void registerAll(List<String> sensorTypes) { /* register를 반복 호출 */ }

    public boolean isManaged(String sensorType) {
        return cache.contains(sensorType);
    }
}
```

- 애플리케이션 기동 시(`@PostConstruct`) Redis(`managed-sensor-types`, Redis Set)에 저장된 전체 목록을 캐시로 적재합니다.
- 등록 시 Redis와 캐시에 함께 반영하여, 여러 인스턴스가 떠 있어도 재시작 시 서로 다른 인스턴스가 등록한 타입을 모두 인식할 수 있습니다.
- `ManagedSensorTypeInitializer`(`ApplicationRunner`)가 기동 시 기본 타입(`TEMPERATURE`, `HUMIDITY`, `CO2`, `LIGHT`)을 항상 등록해두므로, 임계값 이벤트가 한 번도 오지 않은 상태에서도 이 4가지 타입은 관리 대상입니다.

## 3. Repository

`Redis` 외의 저장소로 교체될 가능성을 고려해 인터페이스로 정의하고, Redis 기반 구현체를 각각 둡니다.

```text
ThresholdInfoRepository (interface)
└── ThresholdInfoRedisRepository
    ├── upsert(ThresholdInfoDto)
    ├── findByCultivationId(Long) : Optional<ThresholdInfoDto>
    ├── deleteByCultivationId(Long)
    └── existsByCultivationId(Long)

SensorInfoRepository (interface)
└── SensorInfoRedisRepository
    ├── upsert(SensorInfoDto)
    ├── findByDeviceEuiAndSensorType(String, String, String) : Optional<SensorInfoDto>
    ├── deleteByDeviceEuiAndSensorType(String, String, String)
    └── existsByDeviceEuiAndSensorType(String, String, String)

ManagedSensorTypeRepository (interface)
└── ManagedSensorTypeRedisRepository
    ├── register(String)         (Redis Set에 add — 이미 있으면 아무 동작 안 함)
    ├── isManaged(String)        (Redis Set의 isMember)
    └── findAll() : Set<String>  (Redis Set의 members)
```

### 3-1. Redis Key 설계

| 도메인 | Key 형식 | 예시 |
|---|---|---|
| ThresholdInfo | `threshold:{cultivationId}` | `threshold:1` |
| SensorInfo | `sensor:{deviceEui}:{sensorType}:{unit}` | `sensor:24E124...:TEMPERATURE:°C` |
| ManagedSensorType | `managed-sensor-types` (단일 Redis Set) | - |

- `SensorInfo`의 조회 키가 `cultivationId` 기준이 아니라 `deviceEui`+`sensorType`+`unit` 기준인 이유는, Collector 검증 시점에는 아직 `cultivationId`를 모르기 때문입니다. 오히려 등록된 센서 정보를 조회해 `cultivationId`를 알아내는 것이 검증의 목적입니다.
- Key 조립 로직은 각 구현체 내부 `buildKey()`로 일원화되어 있습니다.

### 3-2. Upsert / 직렬화

- `upsert`는 Redis `SET`(`opsForValue().set()`)을 그대로 사용해 키 존재 여부와 무관하게 항상 덮어씁니다.
- `RedisTemplate`의 Value 직렬화는 Jackson 기반(`ObjectMapper`)을 사용하며, 조회 시 `objectMapper.convertValue(rawValue, XxxDto.class)`로 역직렬화합니다.
- 존재 확인(`existsBy...`)은 값 전체를 역직렬화하지 않고 Redis `EXISTS`(`hasKey()`)만 사용해 가볍게 확인하며, 반환 타입이 `Boolean`(null 가능)이라 `Boolean.TRUE.equals(...)`로 감싸 반환합니다.
